## 1. 问题与目标

同租户已有未删除账号在 Session 权威失效后，应按原 `account_id` 重新授权。数据库保存 Session 密文只代表平台仍持有历史授权材料，不代表 Telegram 当前仍接受 AuthKey；远端撤销、AuthKey 未注册或明确的远端未授权事实发生后，账号必须进入重新授权，而不是创建第二个账号。

当前“Session失效”只计入“登录有问题”，没有进入“继续登录”动作；运营从“新增账号”提交同手机号又收到“账号已存在 / 已在分组”的死路错误。本次目标：

1. `Session失效`、`需重新登录` 和未完成登录状态按原 `account_id` 显示并进入既有登录流。
2. 新增入口命中同租户未删除账号时，返回固定结构化冲突，前端改为原账号重新登录。
3. 保留原账号 ID、分组、用途、任务/群关系、授权和审计历史；只推进登录流并在成功时更新授权材料。

临时代理、网络或同步失败不是 Session 失效证据，不能被本功能自动改写为重新登录。三授权槽都掉线且没有冷备时，仍只能人工验证码/扫码重新登录，不能伪造自动恢复。

## 2. 命令与状态合同

| 命令 | 前提 | 允许副作用 |
| --- | --- | --- |
| `create_new_account` | 同租户不存在该手机号的未删除账号 | 创建账号、分配新账号所需资源；随后由前端显式启动登录 |
| `reauthorize_existing_account` | 原账号处于待登录、等待验证码、等待扫码、等待2FA、需重新登录、Session失效或异常 | 读取原账号、恢复或新建登录流；成功后更新该账号授权状态 |

- `在线` 或其他不适合重新授权的已有账号只打开详情，不自动重登。
- 有效的等待验证码 flow 优先恢复；只有用户明确“重新发送”才请求新验证码。
- 不做静默 upsert，不移动原账号分组/用途，不修改原资料，不在 409 响应时隐式发送 Telegram 验证码。
- 已删除账号仍按现行规则允许重新创建；本专项无迁移。

## 3. 用户流程

```text
账号列表：Session失效 / 需重新登录 / 未完成登录
  -> 点击“继续登录”
  -> 使用原 account_id 打开既有登录弹窗
  -> 恢复有效 code flow，或显式调用 /login/start
  -> code / QR / 2FA 成功后原账号在线

新增入口提交手机号
  -> POST /api/tg-accounts
  -> 无已有账号：创建新账号，前端显式启动登录
  -> 有同租户未删除账号：409 existing_account_requires_relogin
  -> 前端读取原账号详情，清空新增表单
  -> 可重登状态进入原账号登录；其他状态打开详情
```

## 4. API 合同与安全

`POST /api/tg-accounts` 对同租户已有未删除账号返回 HTTP 409：

```json
{
  "detail": {
    "code": "existing_account_requires_relogin",
    "message": "该账号已存在，正在进入重新登录",
    "account_id": 123
  }
}
```

- 后端先按已解析的当前租户查找 `(tenant_id, phone_masked, deleted_at is null)`，再进行新账号配额、分组准入和开发者应用分配；新账号前置校验不能阻断已有账号重新登录。
- 只返回当前租户的 `account_id`，不泄露跨租户账号；不返回完整手机号、验证码、Session、AuthKey 或 2FA。
- 前端只按 HTTP 409 + 固定 `code` 路由，不能解析中文错误文案。
- 原账号详情和 `POST /api/tg-accounts/{account_id}/login/start` 继续执行资源租户与核心功能权限校验。

## 5. 一致性、并发与失败边界

- 重授权不得改变 `tg_accounts.id`、`pool_id`、`account_identity`、任务绑定、群关系或历史流水。
- 应用层命中已有账号时固定走 409；数据库既有唯一性约束继续兜住并发创建。
- 原账号详情读取失败、非结构化 409、400、登录启动失败和后台 401 保持各自现有错误合同，不被伪装为重授权成功。
- 登录启动失败必须留下失败 flow、账号状态、审计和 `trace_id`；不吞错或伪造成功。

## 7. QA 与发布闸门

1. `Session失效` 显示“继续登录”，使用原 `account_id`。
2. 同手机号新增返回结构化 409；原账号数量、ID、分组和状态不变，即使请求携带无效新分组。
3. 前端只对固定 409/code 读取原账号详情并进入登录；在线账号不自动重登。
4. 已删除账号可重新新增；非结构化错误不误路由。
5. 通过后端定向测试、前端数据流测试、前端构建与 `git diff --check`。
6. 发布按 `master -> release -> GitHub Actions Deploy Production`；部署成功只证明运行时部署，真实 Telegram 重新授权须在经授权的账号上取得登录 flow 和远端授权事实后才可标记 `production_fixed`。
